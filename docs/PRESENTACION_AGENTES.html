01Qué es el proyecto

Una herramienta que convierte la intención de un físico en una simulación numérica completa y reproducible.

El usuario describe un potencial cuántico — en texto ("pozo finito de GaAs de 30 nm y 250 meV") o subiendo una imagen (un esquema, una micrografía AFM/SEM) — y el sistema produce:

  • Un diseño paramétrico formal del potencial V(x) o V(x,y) en un DSL JSON auditable.
  • La solución numérica de la ecuación de Schrödinger de masa efectiva (eigenvalores, funciones de onda, densidades |ψ|²) por diferencias finitas.
  • La exportación a COMSOL Multiphysics por tres vías: un archivo .mph nativo que abre directo, un script MATLAB LiveLink .m, y una receta paso a paso en markdown.

La pieza distintiva no es el solver (diferencias finitas es un método estándar): es quién construye el diseño. En lugar de un formulario con sliders o de un algoritmo de ajuste, el diseño lo construye un agente de IA — el mismo LLM que el estudiante ya tiene abierto (Claude Code, Codex, etc.) — que opera la herramienta mediante un CLI, mira el resultado renderizado, lo critica y lo refina en un ciclo cerrado hasta que coincide con la intención del usuario.

Tesis del proyecto Un problema de "descripción → modelo físico" no es un problema de ajuste de curvas: es un problema de diseño que requiere conocimiento físico previo, razonamiento geométrico y verificación visual. Esa combinación es exactamente lo que un agente LLM con herramientas sabe hacer, y lo que ningún método clásico de regresión ofrece.

02¿Qué es un agente de IA?

Un modelo de lenguaje deja de ser un chatbot y se vuelve un agente cuando puede actuar sobre un entorno, observar el resultado y decidir su siguiente paso.

Un LLM "a secas" es una función: texto entra, texto sale. No tiene memoria del mundo, no puede ejecutar nada, y si se equivoca no se entera. Un agente envuelve ese modelo en un bucle de percepción–acción:

Formalmente, un agente combina cuatro ingredientes:

1 Modelo

Un LLM (aquí, el de Claude Code) que aporta razonamiento, conocimiento previo — incluida la física de heteroestructuras — y visión multimodal para leer imágenes AFM y renders.

2 Herramientas (tools)

Acciones ejecutables con contrato definido: correr un comando, leer/escribir archivos, ver una imagen. Son las "manos" del agente. En este proyecto la herramienta central es el CLI qpot.

3 Bucle con retroalimentación

Cada acción devuelve una observación (JSON del solver, un PNG) que entra al contexto del modelo. El agente puede equivocarse y corregirse — eso es lo que lo hace robusto.

4 Contexto e instrucciones

Documentos que le dicen al agente qué rol tiene y cómo operar el entorno. Aquí: AGENTS.md (el manual del agente), PRIMITIVES.md (el contrato del DSL) y CLAUDE.md.

La intuición clave para la presentación: el valor del agente no está en que "sabe la respuesta", sino en que puede verificarla. Un LLM sin herramientas diría "un pozo de 30 nm en GaAs tiene ~3 estados ligados" y podría estar mal. El agente construye el pozo, corre el solver, cuenta los estados ligados en el resultado numérico, y si el render no coincide con lo pedido, lo arregla. La alucinación se filtra contra la realidad del entorno.

03Conceptos frontera para entender agentes

El vocabulario del estado del arte (2025–2026), y qué papel juega cada pieza en este proyecto.

API API de un LLM

Acceso programático al modelo por internet: mandas mensajes, pagas por token. Es como se construyen productos de IA "embebida" — y fue la primera versión de este proyecto (pipeline con la API de Anthropic, hoy archivado en legacy/).

Aquí: se eliminó. El cerebro es el agente que el estudiante ya tiene abierto; costo marginal cero.

Harness Harness (arnés)

La infraestructura que envuelve al modelo y ejecuta el bucle: gestiona el contexto, despacha las tool calls, aplica permisos, reintenta errores. Claude Code es un harness. Sin harness, un LLM no puede tocar nada.

Aquí: el proyecto no implementa su propio harness — se "monta" sobre el que el usuario ya tiene. Además, cada diseño puede llevar una ficha harnex (identidad, propósito, justificación) que lo hace auditable.

Tools Herramientas

Funciones con esquema tipado que el modelo puede invocar: Bash, Read (¡incluye ver imágenes!), Write. El modelo emite la llamada; el harness la ejecuta y devuelve el resultado.

Aquí: el agente usa Bash para operar qpot y Read para mirar render.png — la visión multimodal cierra el loop de verificación.

CLI CLI como interfaz agente↔programa

Hallazgo central del diseño: una interfaz de línea de comandos bien documentada es la API universal para agentes. Cualquier LLM que sepa usar una terminal puede operar la herramienta — sin SDK, sin integración por proveedor.

Aquí: python -m qpot {new, add, set, render, verify, export…}. Las consultas imprimen JSON (legible por máquina); las acciones, mensajes cortos.

Skills Skills / slash-commands

Procedimientos empaquetados que se cargan al contexto bajo demanda: "cuando te pidan X, sigue estos pasos". Extienden al agente sin reentrenar nada — es programación por documentación.

Aquí: el comando /potential (en .claude/commands/) arranca el flujo completo Designer→Verify→Refiner de una sola invocación.

MCP Model Context Protocol

Estándar abierto (Anthropic, 2024; hoy adoptado por todo el ecosistema) para conectar agentes a servicios externos: un servidor MCP publica herramientas y el agente las descubre y usa. Es el "USB de los agentes".

Aquí: no fue necesario — el CLI cumple el mismo papel localmente. Sería el camino natural si la herramienta se ofreciera como servicio remoto (p. ej. un qpot-mcp para usar desde claude.ai).

Ctx Contexto y grounding

El agente solo "sabe" lo que cabe en su ventana de contexto. Por eso los proyectos agénticos serios versionan archivos de contexto (AGENTS.md es un estándar emergente multi-cliente) y anclan cada afirmación a evidencia observable (grounding).

Aquí: la regla de oro del manual: "nunca declares que un potencial está bien sin haber corrido qpot verify y mirado el PNG".

Multi Subagentes / multi-agente

Un agente puede delegar roles a agentes hijos con contexto propio (patrón orquestador–trabajadores). Útil para paralelizar o aislar criterios (el que verifica no es el que diseñó).

Aquí: los roles Designer / Verifier / Refiner pueden correr como subagentes en Claude Code, o secuencialmente en uno solo. El rol es del flujo, no del proceso.

Medios donde se conecta un agente

Un mismo modelo puede operar por distintos "medios", con distintos costos y capacidades. Este proyecto eligió deliberadamente la fila 2:

MedioEjemploCostoAcceso al entorno
API embebida en la apppipeline legacy/ con API Anthropicpor token, recurrentesolo lo que la app le programe
Agente de terminal sobre el repoClaude Code / Codex + CLI qpot ← elegido$0 marginal (suscripción ya existente)total: shell, archivos, imágenes

04Estado del arte e investigación en agentes de IA

De dónde viene la idea, qué dice la literatura, y qué principios de frontera aplica (o anticipa) este proyecto.

Breve historia: cómo llegamos aquí

2022 — razonar en voz alta

Chain-of-Thought y ReAct

Wei et al. muestran que pedir al modelo razonar paso a paso mejora drásticamente su desempeño (Chain-of-Thought). Yao et al. formalizan en ReAct el patrón que define a los agentes modernos: intercalar razonamiento (pensar qué hacer) con acciones (consultar herramientas) y observaciones (leer el resultado). El bucle de la Fig. 1 es, en esencia, ReAct.

2023 — herramientas y autocrítica

Toolformer, function calling, Reflexion, Voyager… y el fracaso de AutoGPT

Toolformer (Schick et al.) demuestra que un LLM puede aprender a invocar APIs; los proveedores lo estandarizan como function calling con esquemas tipados. Reflexion (Shinn et al.) añade autocrítica verbal: el agente analiza su propio fallo y reintenta mejor — el germen del rol Verifier. Voyager (Wang et al.) introduce la biblioteca de skills: procedimientos aprendidos que se guardan y reutilizan (antecedente directo de los skills/slash-commands actuales). Y el hype de AutoGPT/BabyAGI — autonomía total sin verificación — fracasa en tareas reales: lección fundacional de que autonomía sin oráculo diverge.

2024 — el agente toca el mundo real

SWE-agent, computer use, MCP

SWE-agent (Yang et al.) formula la idea de Agent-Computer Interface: el rendimiento del agente depende tanto de la interfaz que se le da como del modelo (justificación directa del diseño del CLI qpot). Anthropic lanza computer use (el agente maneja pantalla/mouse) y publica el Model Context Protocol, que en 2025 adoptan OpenAI, Google y Microsoft como estándar de conexión agente↔servicios.

2025–2026 — harnesses maduros y razonamiento en inferencia

Agentes de código, test-time compute, tareas largas

Los harnesses de terminal (Claude Code, Codex CLI) se vuelven la forma dominante de agente productivo; AGENTS.md emerge como estándar de facto multi-cliente para instruirlos. Los modelos razonadores muestran que "pensar más tiempo" en inferencia (test-time compute) escala el desempeño en problemas difíciles. Y la organización METR mide que la longitud de tarea que un agente completa con 50% de éxito se duplica aproximadamente cada 7 meses — la métrica de progreso agéntico más citada de la frontera.

Workflows vs. agentes: los patrones canónicos

La guía de diseño más influyente (Anthropic, Building Effective Agents, 2024) distingue workflows — flujos con pasos predefinidos por código — de agentes — donde el LLM decide dinámicamente sus pasos — y cataloga los patrones intermedios:

P1 Prompt chaining

Salida de un paso alimenta al siguiente, en secuencia fija. El pipeline legacy/ de este proyecto era exactamente esto.

P2 Routing

Un clasificador dirige la entrada al flujo especializado adecuado (¿es 1D o 2D? ¿texto o imagen?).

P3 Orchestrator–workers

Un agente central delega subtareas a agentes hijos con contexto propio. En Claude Code: subagentes Designer/Verifier.

P4 Evaluator–optimizer

Un rol genera, otro evalúa contra criterios y devuelve feedback; se itera. Es el patrón de este proyecto: Designer genera, qpot verify + Verifier evalúan, Refiner optimiza.

P5 Agente autónomo

Loop abierto: el modelo planifica, actúa y decide cuándo terminar. Es lo que hace el agente sobre el repo, con el humano como aceptación final.

★ Principio rector

"Usa el patrón más simple que funcione." La complejidad agéntica solo se justifica cuando la tarea es abierta — como interpretar una foto AFM ambigua.

El problema central: errores compuestos y el oráculo

El hallazgo más importante de la investigación agéntica es aritmético. Si cada paso del agente acierta con probabilidad p, una tarea de n pasos sin verificación acierta con pn: con 90% por paso y 20 pasos, solo 12% de éxito total. Los agentes que funcionan en producción rompen esa aritmética de una sola forma: verificación externa barata en cada iteración — el compilador para el código, los tests para el software, y aquí el validador + solver + render para la física.

Regla de la frontera: "los agentes funcionan donde verificar es barato" Programación despegó primero porque tiene oráculos gratis (compilar, testear). Este proyecto aplica la misma receta a la física computacional: construimos el oráculo (qpot verify: esquema → rangos físicos → convergencia → estados ligados → render visual) antes de soltar al agente. No es un detalle de implementación: es la razón estructural por la que el sistema converge en pocas iteraciones en lugar de divergir como AutoGPT.

Memoria y context engineering

Un agente solo "sabe" lo que cabe en su ventana de contexto, y la calidad de atención se degrada al llenarla (context rot). La disciplina emergente de context engineering (sucesora del prompt engineering) gestiona ese recurso escaso con tres técnicas que este proyecto usa de forma natural:

  • Estado externo en el filesystem: la memoria durable del agente no es su contexto sino archivos — aquí session/design.json y los artefactos de session/. Cualquier agente (u otro agente, otro día) puede retomar el trabajo leyendo el estado.
  • Instrucciones versionadas y por capas: CLAUDE.md (arranque mínimo) → AGENTS.md (manual completo) → PRIMITIVES.md / COMSOL_MPH.md (contratos que se cargan solo cuando tocan). Cargar justo lo necesario, justo a tiempo.
  • Herramientas que devuelven poco y denso: las consultas de qpot imprimen JSON compacto, no volcados — cada token de observación compite por la atención del modelo.

Seguridad y modos de fallo

Riesgo Alucinación

El modelo afirma algo falso con confianza. Mitigación estándar: grounding — toda afirmación debe anclarse a una observación. Aquí: regla de oro "nunca declares el potencial correcto sin correr verify y mirar el PNG".

Riesgo Inyección de prompt

Contenido malicioso en los datos que el agente lee (archivos, webs) intenta darle órdenes. Mitigación: tratar datos como datos, sandboxing, permisos por acción. Aquí la superficie es mínima: el agente solo opera un CLI local.

Riesgo Ejecución de código no confiable

Si el agente puede escribir expresiones evaluables, puede (por error o manipulación) ejecutar cualquier cosa. Aquí: raw_expr pasa por sandbox AST con whitelist — nunca un eval() desnudo.

Riesgo Reward hacking / Goodhart

El agente optimiza la métrica y no la intención ("pasan los tests" ≠ "el código es correcto"). Mitigación: señales múltiples e independientes. Aquí: validador numérico + solver + crítica visual + aceptación humana — cuatro jueces distintos.

El consenso de la frontera: la autonomía se gradúa, no se regala. Acciones reversibles → el agente procede; acciones costosas o irreversibles → confirmación humana. En este proyecto la "acción costosa" es abrir la JVM de COMSOL, y por eso existe la puerta de validación pre-export.

La línea de investigación más cercana a este trabajo es la de agentes científicos, y todos convergen en el mismo patrón — el LLM propone, un instrumento verificado dispone:

Tendencias de frontera a mencionar en la discusión

  • Test-time compute: escalar el "tiempo de pensar" en inferencia (modelos razonadores) mejora tareas difíciles sin reentrenar — complementa el escalado clásico de parámetros/datos.
  • Horizonte de tareas (METR): la duración de tareas completables con 50% de éxito se duplica ~cada 7 meses; los agentes actuales sostienen tareas de horas.
  • Interoperabilidad: MCP (agente↔herramientas) y protocolos agente↔agente apuntan a un ecosistema donde los agentes componen servicios como hoy las apps componen APIs.
  • Del prompt al entorno: la ventaja competitiva se movió de "escribir buenos prompts" a diseñar buenos entornos — herramientas, contratos, oráculos y documentación para agentes. Este proyecto es un ejercicio completo de esa disciplina: qpot + AGENTS.md + verify son el entorno.

05¿Por qué un agente y no regresión simbólica?

La regresión simbólica responde "¿qué fórmula ajusta estos datos?". Nuestro problema es otro: "¿qué modelo físico corresponde a esta intención?".

La regresión simbólica (SR: programación genética, PySR, SINDy…) busca en el espacio de expresiones matemáticas la que minimiza el error contra un conjunto de datos numéricos. Es una técnica poderosa — para el problema para el que fue diseñada. El nuestro no lo es, por cinco razones:

Regresión simbólicaAgente + DSL de primitivas (este proyecto)
EntradaRequiere datos (x, V) ya medidos. De una frase o una foto AFM no hay tabla que ajustar.Lenguaje natural e imágenes directamente — el LLM es multimodal.
SalidaUna expresión arbitraria (p. ej. 0.31·tanh(x²−sin x)): ajusta, pero no significa nada físico ni se transfiere a COMSOL como geometría.Composición de primitivas físicas con nombre y unidades (pozo, anillo, Coulomb, campo Stark) — cada parámetro es un slider barrible en COMSOL.
Conocimiento previoNinguno: no sabe que un punto cuántico de GaAs mide 10–100 nm y 50–500 meV.El agente aplica escalas físicas de sanity-check (§4 de AGENTS.md) y masas efectivas correctas por material.
Restricciones estructuralesDifícil imponer "es una corona entre una hipocicloide y una epicicloide".La geometría se declara: regiones + operaciones booleanas (union/intersection/complement), estilo COMSOL.
VerificaciónSolo error numérico de ajuste; puede sobreajustar sin aviso.Doble: señales objetivas (validador + convergencia del solver + estados ligados) y crítica visual del render contra la imagen fuente.

Dicho de otra forma: la SR hace interpolación en el espacio de fórmulas; el agente hace diseño en el espacio de modelos físicos. El paralelo correcto de este proyecto no es un ajustador de curvas sino Text2CAD: de una descripción, a un objeto paramétrico editable, con un humano (y un solver) en el loop de aceptación.

Y donde la SR sí sería útil… …es complementaria, no rival: si mañana hubiera datos experimentales de espectros, un módulo de SR podría proponer correcciones al potencial dentro del DSL. El diseño por primitivas no lo excluye; lo estructura.

06Arquitectura y decisiones de diseño

Cada decisión respondió a un problema concreto que apareció en el desarrollo.

La arquitectura en una figura

Evolución: las decisiones y su porqué

Versión 1 — punto de partida

App Streamlit + pipeline multi-agente vía API de Anthropic

Cuatro agentes programados (vision, designer, verifier, refiner en legacy/) llamaban a la API por cada iteración. Problema: costo por token recurrente, latencia, y una ironía — el estudiante ya tenía un LLM más capaz abierto en su editor, y le estábamos cobrando otro.

Decisión clave — giro de arquitectura

Mover el cerebro al agente del usuario (estilo Text2CAD) → nace el CLI qpot

Por qué: API $0, mejor modelo (el harness del usuario siempre trae el más reciente), multimodalidad gratis, y portabilidad: cualquier agente que sepa usar una terminal (Claude Code, Codex, Antigravity) opera la herramienta. El conocimiento de los prompts se destiló en AGENTS.md: los "agentes" pasaron de ser código a ser documentación ejecutable por un LLM.

Decisión — representación

DSL JSON de primitivas físicas como única fuente de verdad

Por qué: restringe al agente a un espacio físicamente significativo (no puede "alucinar" un potencial sin sentido: solo componer piezas válidas), es auditable por el humano, y es traducible 1:1 a geometría COMSOL. 8 regiones + 11 perfiles + operaciones mask/where/union/intersection/complement, con parámetros nombrados (R1, R2, n, Vb) al estilo COMSOL para que un cambio se propague y los barridos sobrevivan a la exportación.

Decisión — confiabilidad

Verificación por dos canales: señales objetivas + ojos del agente

Por qué: a un LLM no se le pide fe. qpot verify combina un validador numérico sin IA (esquema, rangos físicos, NaN, solapes de zonas), el solver como oráculo (convergencia, nº de estados ligados) y el render PNG que el agente debe mirar y calificar 0–10 contra el objetivo. Regla de oro: ver para creer.

Decisión — seguridad

Sandbox AST para raw_expr

Por qué: si el agente escribe expresiones libres, no pueden pasar por un eval() desnudo. Se validan por árbol sintáctico contra whitelist estricta (solo x, y, r, theta, funciones numpy fijas; sin atributos, sin subscripts, sin dunders; límite 500 chars / profundidad 25).

Decisión — trazabilidad

Ficha harnex + puerta de validación pre-export

Por qué: cada diseño puede llevar un encabezado versionable (id, propósito, justificación de material y dominio, observables esperados) que lo convierte en un componente auditable de laboratorio. Y export_mph() corre validate_for_comsol_export() antes de abrir COMSOL: si el Design no es exportable, falla con la lista de razones sin llegar a lanzar la JVM.

Decisión — salida

Exportación por tres vías con degradación elegante

Por qué: no todos los equipos tienen MATLAB o la librería MPh. recipe (markdown) funciona siempre; .m si hay MATLAB+LiveLink; .mph nativo si hay MPh+COMSOL — y si MPh falta, el sistema cae con gracia a la receta en lugar de romperse.

07El camino a COMSOL: lo que costó hacerlo funcionar

Generar un .mph que abra y resuelva sin MATLAB fue la parte más dura del desarrollo. Cada regla de esta sección costó un intento fallido.

El objetivo: que python -m qpot export --format mph produzca un modelo COMSOL con geometría por entidades (no una imagen del potencial: cuadrado de dominio + curvas paramétricas reales), la interfaz de Ecuación de Schrödinger con masa efectiva y potencial por dominio, un estudio de valor propio, y los parámetros nombrados preservados para poder hacer barridos. Todo vía MPh, el puente Python→JVM→API Java de COMSOL.

Los tres problemas que hubo que resolver

1 La matriz Java/MPh/jpype

El error "Java version too old" no venía de COMSOL sino de jpype (≥1.6 exige Java 11, y COMSOL 5.6 trae Java 8). Solución: fijar MPh==1.2.3 + jpype1==1.5.2, y JAVA_HOME vacío o apuntando al JRE de COMSOL. También: matar procesos comsolmphserver huérfanos entre corridas.

2 El potencial por defecto contamina todo

La interfaz Schrödinger trae un nodo de potencial por defecto (ve1) que es armónico y cubre todos los dominios. Si queda activo, la física entera sale mal aunque tus nodos estén bien. Regla nº 1: deshabilitarlo siempre (ve1.active(False)).

3 Repartir V por dominio sin conocer la numeración

Al "formar unión", COMSOL numera los dominios de forma impredecible desde Python. Solución robusta: evaluar la máscara de cada región en una grilla, tomar por componente conexa el punto más interior (distance_transform_edt), y crear ahí una Ball selection de radio 0.5 nm que "pesca" el dominio correcto. Cada dominio queda en exactamente un nodo de potencial: partición disjunta y completa.

Estructura del modelo generado (orden obligatorio)

  1. Parámetros globales con unidades: R1 = 12[nm], R2 = 28[nm], n = 7, Vb = 0.228[eV], m_eff, Ldom.
  2. Geometría 2D: Square de dominio + cada región como entidad (Circle, Ellipse, Rectangle, y ParametricCurve con x(s), y(s) en función de los parámetros para epicicloides/hipocicloides/superelipses) + Formar unión.
  3. Física: interfaz SchrodingerEquation — masa efectiva m_eff, default ve1 deshabilitado, un nodo ElectronPotentialEnergy por zona con su Ball/Union selection.
  4. Malla automática fina + Estudio de valor propio (neigs, shift 0).
  5. Guardar — y envolver client.disconnect() en try/except: en modo standalone lanza un error después de que el .mph ya quedó en disco (ruido, no fallo).

Gotchas finos de jpype que costaron intentos: los enteros ambiguos exigen JInt(2) (si no, "Ambiguous overloads"); las selecciones deben referenciarse por el tag real que devuelve nodo.java.tag(), no por el nombre con que las creaste.

Verificación sin COMSOL Un .mph es un ZIP: test_mph.py (test de regresión, no necesita COMSOL) inspecciona dmodel.xml y verifica que la interfaz sea SchrodingerEquation, que ve1 diga DISABLED, que las curvas paramétricas usen los parámetros, y que el reparto región/complemento sea disjunto y completo. Además qpot verify chequea solapes de zonas (zone_overlap) desde el propio Design. Todo el conocimiento quedó documentado en COMSOL_MPH.md — la "guía definitiva" que cualquier agente futuro debe leer antes de tocar el exportador.

08Fundamento físico y numérico

El agente diseña; la física la resuelve código determinista y validado.

Modelo físico

Un electrón en la banda de conducción de una heteroestructura semiconductora, con la aproximación de masa efectiva:

H = −(ħ²/2m*)∇² + V(r)

m* por material (GaAs 0.067·m₀, InAs 0.023, Si 0.191…; Vurgaftman et al. 2001). V incluye heterouniones, impurezas Coulomb regularizadas y campos eléctricos (efecto Stark). Coordenadas en nm, energías en eV.

Solver numérico

Diferencias finitas de 2º orden. En 1D el Hamiltoniano es tridiagonal → diagonalización directa. En 2D, stencil de 5 puntos sobre grilla N×N → matriz sparse enorme, se extraen solo los N estados de menor energía con el algoritmo de Arnoldi (scipy.sparse.linalg.eigs). Frontera: ψ=0 en los bordes.

Síntesis para la discusión

El aporte del proyecto es metodológico además de funcional: demuestra un patrón replicable para instrumentos científicos — separar el cerebro (agente LLM, gratuito, intercambiable) del músculo (solver y exportadores deterministas, validados), unidos por un contrato explícito (el DSL JSON) y un ciclo de verificación con señales objetivas. El agente nunca es la autoridad física: es el diseñador que propone y el crítico que compara; la autoridad son el validador, el solver y los ojos del usuario sobre artefactos siempre inspeccionables.
